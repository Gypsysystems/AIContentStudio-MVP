---
name: Topic history from checkpoints
description: Why authored topic history is projected from immutable project checkpoints and how partial reads affect it
---

Read-only authored topic history is a projection of committed project checkpoints, not a stream of every edit. A topic version exists only where a saved checkpoint contains it; stable topic identity links renames and reorders, while ambiguous legacy identities must remain unresolved. Metadata-only reads can validate the saved record and manifest, but cannot claim that archived file bytes were verified. A missing or unsupported checkpoint makes change comparisons across that gap unknown. A null parent link is a baseline only when the authorized history has one unambiguous root; malformed, self-referential, or conflicting root links cannot support a change claim. All visible parent labels must express the same uncertainty as the change summary. For file timelines, a digest-valid but semantically unusable record or manifest is unknown, and that uncertainty propagates to descendants instead of certifying continuity.

**Why:** Separate topic snapshots would diverge from existing immutable project snapshots and imply coverage between checkpoints that the app never recorded. Treating nonadjacent readable checkpoints as adjacent can falsely label content unchanged. Digest-valid metadata can still contain semantically ambiguous ancestry or malformed source references; a self-link can falsely suggest no changes, and a stale "first checkpoint" label can contradict an unknown summary. A readable but unsupported ancestor is not proof of a complete file timeline. Full archive verification requires reading the actual saved bytes.

**How to apply:** Keep future component-history browsing derived from committed, project-scoped checkpoints. Check direct-parent identity and root uniqueness against the authorized list before interpreting ancestry; check each saved file manifest and its source references before reporting presence or absence, including those of ancestors. Keep summary and metadata labels consistent. Do not infer edits or source references from current project state; present partial histories and integrity scope explicitly, and use the full checkpoint read when byte-level integrity is required.
